# 故障排查

按「现象」查。每条给出原因和可执行的处理方式。

## 双击 start.bat 没反应，或窗口一闪而过

最常见的原因是 **`start.bat` 变成了 LF 换行**。cmd.exe 只认 CRLF，解析到多行 `if (...)` 块就中断，里面的 `python app.py` 根本不会执行。

验证方法：

```bash
python -c "d=open('start.bat','rb').read(); print('CRLF', d.count(b'\r\n'), 'LF-only', d.count(b'\n')-d.count(b'\r\n'))"
```

如果 `CRLF` 是 0，说明是纯 LF，转换一下：

```bash
python -c "d=open('start.bat','rb').read().replace(b'\r\n',b'\n').replace(b'\n',b'\r\n');open('start.bat','wb').write(d)"
```

`git clone` 时如果 `core.autocrlf=false`，也会得到 LF 版本。可用 `.gitattributes` 固定：`*.bat text eol=crlf`。

另一种可能：这台机器的 `python` 不在 PATH 里。此时 bat 会停在 `[ERROR] Python not found` 并 `pause`，窗口不会闪退，能看到提示。

## 黑窗口出现了，但过了三十多秒才弹出页面

启动阶段在探测端口时用了 `urllib`，而机器设了系统代理（`HTTP_PROXY`）。`urllib` 访问 `127.0.0.1` 的**未监听端口**不会立即收到 RST，而是等满超时（默认 1 秒）；串行探 30 个端口就是 30 秒。

当前版本已改为 `socket.connect_ex()` 毫秒级探活，并用 `build_opener(ProxyHandler({}))` 绕过代理。若你改过代码又出现此问题，检查是不是把探测逻辑改回了 `urlopen`。

## 浏览器没有自动打开，但黑窗口里有地址

程序做了三层兜底：`os.startfile` → `webbrowser` → `cmd /c start`。三层都失败通常是默认浏览器关联损坏。

直接手动复制窗口里那行 `http://127.0.0.1:8731/` 到浏览器打开即可，功能不受影响。

## 页面能打开，但点「开始朗读」一直转圈

先看进度文案是停在「正在准备」还是「正在合成 x/y 段」。

**停在「正在准备」**：请求没到服务端。检查黑窗口是否还在运行；若已关闭，服务已停，页面只是静态残留。

**停在「正在合成」不动**：多半是网络问题。看黑窗口有无异常输出。微软接口对同一出口 IP 有频率限制，连续合成大文本容易触发。

**直接报错**：错误文案会显示在弹层里。`403` 或 `Invalid response status` 表示接口拒绝，返回后重试一次通常能过；持续失败说明出口 IP 被限流，换网络或等一段时间。

## 高亮比声音慢半拍 / 越到后面偏得越多

**越到后面偏得越多**，说明时间轴补偿公式被改坏了。补偿必须用字节数换算：

```python
base_ticks = cum_bytes * 8 * TICKS_PER_SEC // 48000
```

这个公式成立的前提是输出为 **48kbps 恒定码率单声道 MP3**。如果改过 edge-tts 的输出格式（换比特率、换采样率、换成立体声），`48000` 这个常量必须同步改成实际比特率，否则每片都会累积误差。

**整体慢半拍但比例一致**，通常是前端用了 `audio.currentTime` 之外的时钟（例如自己维护的计时器）。以 `timeupdate` 事件为准。

## 拖动进度条无效，或总时长显示 Infinity

服务端的 `Range` 处理缺失或损坏。浏览器对长 MP3 需要 206 Partial Content 才能定位。

用 curl 验证：

```bash
curl -s -o /dev/null -D - -H "Range: bytes=1000-1999" http://127.0.0.1:8731/audio/<key>.mp3
```

正常应返回 `206` 且带 `Content-Range: bytes 1000-1999/<总长>`。返回 `200` 说明走了整文件分支，`_file()` 里的 `Range` 解析有问题。

## 点播放没声音，或按钮没反应

浏览器有自动播放策略：没有用户手势时 `play()` 会被拒绝。当前实现是合成完成后尝试自动播放，被拒绝时静默忽略——**手动点一下播放按钮即可**。

如果手动点也没声音，检查系统音量、以及音频是否真的生成（`cache/` 目录下应有对应 `.mp3`，两万字约 26MB）。

## 提示「文本过长」

上限 30 万字（`MAX_CHARS`）。超过请分两次读，或改大这个常量——但要注意：75 分钟音频约 26MB，300 万字的音频会让浏览器内存吃紧。

## 端口被占用

启动时从 8731 开始顺延到 8740。若这些端口都被占用，会落在更后面的端口——看黑窗口里打印的实际地址。

如果已有实例在跑，再双击一次不会起第二个进程，只会把页面重新打开一次。

## 排查顺序

遇到问题按这个顺序走，能覆盖九成情况：

1. 黑窗口还在不在——不在就是服务停了，重启
2. 黑窗口里有没有报错文字——有就照报错查
3. 访问 `http://127.0.0.1:<端口>/api/ping`，应返回含 `readaloud` 的 JSON
4. 看 `cache/` 目录有没有新增 `.mp3`——有音频说明合成成功，问题在前端；没有说明卡在合成
5. 用 `python scripts/install.py --skip-deps` 重跑一次冒烟测试，确认接口通不通

## 判断"是否正常"的三条标准

改完代码或换环境后，用这三条验收：

1. 三千字文本合成完成后，抽查第 1/10/20/30/40 段的时间占比与字数占比，偏差应小于 1%
2. 点击任意句子，`audio.currentTime` 与对应 span 的 `t` 误差小于 0.5 秒
3. 双击 `start.bat`，3–5 秒内浏览器自动打开
